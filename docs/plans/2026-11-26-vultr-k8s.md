# Vultr k8s and k8s-ha Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Vultr runs `k8s` and `k8s-ha` with the same lifecycle as Linode (deploy, scale, backup, destroy, restore, failover), and `--provider vultr` runs `compose`, `k8s` and `k8s-ha`. The default e2e selection grows from 11 to 13 scenarios; Part C brings it to 15.

**Architecture:** A new Pulumi program `vultr-k8s.js`, shaped like `linode-k8s.js` (a reserved IP given to the master at create, no CCM, k3s's embedded cloud controller, a provider id from metadata) and like `digitalocean-k8s.js` where Vultr has no fixed private addresses (the db and workers wait on the master's VPC address). The boot scripts read Vultr's `/v1.json` metadata in one shared include and find the private interface at boot. Storage is vultr-csi v0.19.1 with its registry.k8s.io sidecars mirrored, our own StorageClass, and a volume size floor because the driver passes small requests straight to an API that refuses them. Every difference reaches shared code through provider class members.

**Tech Stack:** Node ESM CLI, `@ediri/vultr` 2.27.1, k3s v1.37.2+k3s1, bash cloud-init (no apt, jq or docker), vitest.

**Spec:** `docs/specs/2026-11-26-k8s-everywhere-design.md` (on main since #588), Part B and the Shared decisions of Parts B and C. Line numbers below were read on main 4e1d5de5; re-find a seam by its name if it moved.

## Global Constraints

### Repo rules (every task)

- Conventional Commits. Commit with `git commit -F <msgfile> -- <paths>`, pathspecs only; `git add` new files first. Check the staged diff before committing (shared checkout).
- Never `--no-verify`. The pre-commit hook runs the unit suite, so every task ends green.
- The hook does not run CI's other Lint gates. Before every commit, run `pnpm lint:infra` (gitleaks over `origin/main..HEAD`), `pnpm unused` (knip) and `pnpm dupes` (jscpd) as well, and fix what they find.
- No `!:` and no `BREAKING CHANGE` footer. A breaking change gets a "Compatibility note" paragraph in the body instead.
- Every commit message ends with the line `Claude-Session: https://claude.ai/code/session_01SK1vqQLM9B9SaK3Q9Hxjgo`.
- No em or en dashes in user-facing copy (CLI output, errors, docs, README, site). No emoji.
- One dotenv dialect: parse with `util.parseEnv`, write with `formatDotenvLine`.
- A command whose captured output holds a secret (a kubeconfig, a Secret, a server's `.env` or docker login) passes `secret: true` to its runner (#592); `tests/unit/lib/secret-read-census.test.ts` walks every such read.
- The ghcr pull credential goes only through `resolveGhcrPull` in `src/lib/deploy/ghcr-pull.js` and, on compose servers, `ensureGhcrLoginOn` (#592). No server ever gets `gh auth token`.

- No provider-id branches in shared deploy, HA, failover or destroy code. A difference goes through a provider class member.
- No retry ladders. A bounded wait for a boot condition (metadata, an interface, the API server) is fine; stacked retries around a flaky dependency are not.
- x86-64 only.
- Boot scripts stay under the repo caps: 28 KiB rendered for worker and db, 31 KiB for the master.
- No real servers, no cloud resources, no state-changing cloud API calls, no workflow dispatch in any task. Real e2e runs after Parts A, B and C have all merged.

- Tests per AGENTS.md: `pnpm test:unit <file>` for one file, `pnpm test:unit` for the suite, `pnpm lint`, `pnpm test:integration` (Docker), `pnpm test:prepush` for the whole local gate.

### Vultr facts (verify-before-coding, settled 2026-11-25)

Read-only sources only: the installed SDK, upstream source, Vultr's docs and API reference, and public GETs (`/v2/regions`, `/v2/plans`, `/v2/os`).

1. **Private interface.** Not pinned. cloud-init on Vultr configures `interfaces[0]` as the public DHCP interface and every other interface statically from metadata before user scripts run (canonical/cloud-init `cloudinit/sources/helpers/vultr.py`, `generate_network_config`). The boot script reads the private address from metadata and takes the kernel interface that holds it (Task 1).
2. **Firewall and VPC.** Vultr's docs do not say whether a firewall group filters VPC traffic; the FAQ says only that it does not filter outgoing traffic and is not enforced until it has a rule (docs.vultr.com/products/network/firewall). The program adds explicit accept rules from the VPC subnet (TCP and UDP `1:65535`, ICMP), which is correct either way. A VPC is joined only by an instance of the same account attached by the VPC's id (`attach_vpc`, Vultr API); nothing outside the account can attach.
3. **CSI distribution.** vultr-csi ships versioned manifests in its repo, not as release assets: `https://raw.githubusercontent.com/vultr/vultr-csi/v0.19.1/docs/releases/v0.19.1.yml` (latest release v0.19.1, 2026-10-01). That URL matches `scripts/version-channel.mjs` `DRIVER_URL` as repo `vultr/vultr-csi`, tag `v0.19.1`, and its `go.mod` exists at the tag.
4. **volumeHandle.** The Vultr block storage id, a UUID (`VolumeId: volume.ID`, vultr-csi v0.19.1 `driver/controller.go`). The volume's label is the CSI request name, `pvc-<16 hex>` (provisioner `--volume-name-uuid-length=16`). Topology key `region` (`driver/node.go` `NodeGetInfo`). Block volumes carry no tags.
5. **Metadata.** `GET http://169.254.169.254/v1.json`, no header needed (vultr/metadata Go client; cloud-init sends `Metadata-Token: cloudinit`, harmless). Fields used: `instance-v2-id` (the API instance UUID), `hostname`, `interfaces[]` with `network-type` (`public` or `private`) and `ipv4.address`.
6. **User-data size limit.** Undocumented (Vultr API create-instance takes base64 `user_data` with no stated limit). The scripts stay under the repo caps; the first real create is the proof.
7. **Reserved IP at create.** Yes. `Instance.reservedIpId` is "ID of the floating IP to use as the main IP of this server" (`node_modules/@ediri/vultr/instance.d.ts`; REST `reserved_ipv4`). It is ForceNew, as are `ssh_key_ids`, `hostname`, `region` and `os_id`; `plan`, `user_data` and `vpc_ids` update in place (terraform-provider-vultr `resource_vultr_instance.go`). `K8S_FLOATING_IP = true` stands.

Further facts the tasks bind to:

- **VPC resource.** `vultr.Vpc` with `Instance.vpcIds`. `Vpc2` and `vpc2Ids` are deprecated in the SDK ("Use `vultr.Vpc` instead", `vpc2.d.ts`, `instance.d.ts`). `VpcArgs`: `description`, `region`, `v4Subnet`, `v4SubnetMask`, no tags. Limit: 5 VPCs per location (docs.vultr.com/products/network/vpc-networks/faq).
- **Master's VPC address.** `Instance.internalIp` is set when one VPC is attached (terraform-provider-vultr issue 373) and blank when a VPC and a VPC 2.0 are both attached (issue 173). Attach exactly one VPC per instance. The SDK exposes no other VPC address.
- **Reserved IP API.** Object fields `id`, `region`, `ip_type`, `subnet` (the address), `subnet_size`, `label`, `instance_id`. Delete is by id (`DELETE /reserved-ips/{id}`), so delete by address lists first and matches `subnet`. `ReservedIpArgs` takes `label` but no tags.
- **Block storage by region** (public `GET /v2/regions`, 2026-11-25): ams, ewr, lax, lhr, ord and sgp sell NVMe (`block_storage_high_perf`); **sjc sells only HDD** (`block_storage_storage_opt`), syd only NVMe. `sjc` cannot run k8s.
- **Block sizes.** NVMe (`high_perf`) volumes are 10 to 10,000 GB (Vultr API `POST /v2/blocks`). vultr-csi passes a PVC's request through unrounded (`getStorageBytes`, `SizeGB = size / GiB`), so a 1Gi or 5Gi claim fails. Our add-on PVCs request 1Gi (redis and one parked add-on) and 5Gi (grafana and another parked add-on).
- **CSI workloads** (v0.19.1 manifest, kube-system): StatefulSet `csi-vultr-controller` (label `app=csi-vultr-controller`, replicas 2, required pod anti-affinity on hostname, PodDisruptionBudget minAvailable 1, no tolerations) with containers `csi-provisioner` v3.4.0, `csi-attacher` v4.1.0, `csi-resizer` v1.7.0, `csi-snapshotter` v8.4.0 (all `registry.k8s.io/sig-storage/...`) and `csi-vultr-plugin` `vultr/vultr-csi:v0.19.1`, which reads Secret `kube-system/vultr-csi` key `api-key`. DaemonSet `csi-vultr-node` (label `app=csi-vultr-node`, hostNetwork, **no tolerations**) with `driver-registrar` (`registry.k8s.io/sig-storage/csi-node-driver-registrar:v2.7.0`) and `csi-vultr-plugin` (`imagePullPolicy: Always`). The manifest's own StorageClasses (`vultr-block-storage` and five more) carry no default-class annotation. No snapshot CRDs are shipped; the snapshotter sidecar does not exit without them (external-snapshotter v8.4.0 `cmd/csi-snapshotter/main.go` has no CRD check).
- **Sidecar amd64 digests** (`docker buildx imagetools inspect --raw`, 2026-11-25): csi-provisioner v3.4.0 `sha256:7f0d080e35ac455c52956e451b8d230c1eca1a8e0d943fdb657df4e093d03d0f`; csi-attacher v4.1.0 `sha256:b98eb657dfc0ff4ccf3d69a8d68a752b71f25cf04a7277cd272f5dedea6f72c8`; csi-resizer v1.7.0 `sha256:b00685aa6512da6488e824a11fbb40e1689cf0803dde02e7b5eaad1d95597d90`; csi-snapshotter v8.4.0 `sha256:d72c79ae3db2e77480833daea1a50638b319b6d14564f9e425ffa74595139a19`; csi-node-driver-registrar v2.7.0 `sha256:8e89f0ddbd0f8586b3803ca1084e5b2cb562f874dd990adff26f19ca0265e932`. Re-read each before pinning.
- **OS image.** `os_id` 2760 is "Ubuntu 26.04 LTS x64" (public `GET /v2/os`), the compose image.
- **Plans** (public `GET /v2/plans`, 2026-11-25, all sold in every Vultr region we list): vc2-1c-2gb $10, vc2-2c-4gb $20, vc2-4c-8gb $40, vhf-1c-2gb $12 (1 vCPU, 2 GB, 64 GB disk), vhf-2c-4gb $24, vhf-3c-8gb $48 (3 vCPU, 8 GB, 256 GB disk). Vultr refuses plan downgrades.
- **Prices for the cost grid.** Reserved IPv4 $0.004 an hour, $3 a month (docs.vultr.com/support/products/network/are-reserved-ips-free); NVMe block storage $1 per 10 GB a month (www.vultr.com/products/block-storage/). The implementer re-reads both and records the date.

The channel already holds k3s patches for Linode's driver (minor 35; channel run of 2026-11-25: "k3s v1.37.2+k3s1 left out: linode/linode-blockstorage-csi-driver v1.1.5 not built for this minor"). ### Decisions this plan makes

- **Flannel stays on its default (vxlan), as on Linode and DigitalOcean.** The spec says both "same shape as Linode" and "WireGuard-native flannel as on the others"; only Hetzner runs `--flannel-backend=wireguard-native` (the comment in `do-master-init.sh` says it was Hetzner-specific). The plan follows Linode. Switching is one flag on the server line if Brandon wants it.
- **VPC subnet.** `/24` per cluster from the same FNV hash DigitalOcean uses, inside `10.128.0.0/10` (clear of k3s's 10.42/16 and 10.43/16 and the 10.99 WireGuard transport). `/24` is the mask Vultr's own docs example uses; a pinned per-cluster range keeps an HA pair's two VPCs apart.
- **`K8S_UNSUPPORTED_REGIONS = ['sjc']`** with `k8sRegionProblem`, as Linode does for its regions without a VPC.
- **Sizes.** master and worker `['vc2-2c-4gb', 'vhf-2c-4gb']`, db `['vc2-1c-2gb', 'vhf-1c-2gb']`; the picker takes the cheapest orderable, one CPU class across an HA pair. A primary k8s cluster in ewr is $50 a month in servers.
- **StorageClass** `vultr-block-storage-vibecarbon`: provisioner `block.csi.vultr.com`, `reclaimPolicy: Delete`, `allowVolumeExpansion: true`, `volumeBindingMode: WaitForFirstConsumer`, parameters `storage_type: "block"`, `disk_type: "nvme"`.
- **Volume floor.** A provider member `K8S_MIN_VOLUME_GI` (base 0, Vultr 10) raises every PVC request below it at render time. Hetzner's and Linode's drivers round up themselves; Vultr's does not.
- **Reserved IP attribution.** Label `${clusterName}-ingress`. On Vultr, a reserved IP is "labelled project P, environment E" exactly when its label is `${P}-${E}-ingress`.
- **CSI volumes on destroy are attributed by captured id only.** A provider member `ORPHAN_VOLUME_REGION_GUESS` (base true, Vultr false) turns the `pvc-in-cluster-region` heuristic into a reported deferral for Vultr, per the spec's "never by a region-wide guess".
- **The driver container stays on Docker Hub.** Repo policy mirrors only the registry.k8s.io sidecars (`src/lib/images.js`, comment above `CSI_SIDECAR_MIRRORS`); Linode's driver container is not mirrored either.
- **`K8S_RETIRED_CLOUD_SECRETS`** carries Linode's `kube-system/hcloud` entry. An older generated project's `deploy.yml` writes that Secret into any cluster it deploys to, whatever the provider. Vultr has no older boot script, so no boot-written Secret is retired.

## Staging: censuses walk Vultr before the tiers turn on

Most k8s censuses pick their providers with `SUPPORTED_TIERS.includes('k8s')`, and several also compare that set with files on disk (`tests/unit/providers/iac-dispatch.test.ts`, `tests/unit/iac/k3s-token-census.test.ts`, the boot-script walk in `tests/unit/deploy/k3s-server-flags.test.ts`). Vultr's scripts and program land in Tasks 1 to 5, but its tiers turn on only in Task 6. Without a change those censuses would either fail at Task 1 or skip Vultr until Task 6.

Task 1 adds `tests/_shared/k8s-built-ahead.ts`:

- `export const K8S_BUILT_AHEAD: readonly string[] = ['vultr'];` lists providers whose k8s code is landing before their tier is sold.
- `export function k8sCensusProviders()` returns the `[id, ProviderClass]` entries of `PROVIDERS` whose `SUPPORTED_TIERS` includes `'k8s'`, then those in `K8S_BUILT_AHEAD`, in registry order.
- Its guard test fails if an entry is not a registered provider or already sells `k8s`, so the list cannot rot. Task 6 sets it to `[]`.

Each task switches the censuses its own code makes true for Vultr from `SUPPORTED_TIERS.includes('k8s')` to `k8sCensusProviders()`, and names them. After Task 6 the helper and `SUPPORTED_TIERS` give the same set. Part C may extend the same list (a trivial merge conflict if the parts run side by side).

done
read -r PUBLIC_IP PRIVATE_IP NODE_ID NODE_NAME <<VMETAEOF
$(printf '%s' "$VMETA" | python3 -I -c '
import json, sys
try:
    m = json.load(sys.stdin)
except ValueError:
    m = {}
def addr(kind):
    for i in m.get("interfaces") or []:
        if i.get("network-type") == kind and (i.get("ipv4") or {}).get("address"):
            return i["ipv4"]["address"]
    return "-"
print(addr("public"), addr("private"), m.get("instance-v2-id") or "-", m.get("hostname") or "-")
')
VMETAEOF
[ "$PUBLIC_IP" != "-" ] && [ -n "$PUBLIC_IP" ] || { echo "FATAL: no public address in Vultr metadata" >&2; exit 1; }
[ "$PRIVATE_IP" != "-" ] || { echo "FATAL: no private (VPC) address in Vultr metadata; is the instance attached to the cluster VPC?" >&2; exit 1; }
[ "$NODE_ID" != "-" ] || { echo "FATAL: no instance-v2-id in Vultr metadata" >&2; exit 1; }
PRIVATE_IFACE=""
for _ in $(seq 1 15); do
  PRIVATE_IFACE=$(ip -o -4 addr show | awk -v ip="$PRIVATE_IP" '{ split($4, a, "/"); if (a[1] == ip) { print $2; exit } }')
  [ -n "$PRIVATE_IFACE" ] && break

done

## Open risks

- **Metadata assumptions.** That `network-type` reads `private` for a VPC interface rests on the metadata client and cloud-init's helper, not on a live read. The include fails loudly rather than joining over the public network.
- **Firewall and VPC traffic.** If the firewall group filters VPC traffic, `setFirewallRules`' delete-then-recreate (on `applyOperatorCidrs` and the k8s-ha replication rule) drops node-to-node traffic for a few seconds while the rules are recreated.
- **5 VPCs per location.** An account with three k8s environments and a k8s-ha standby in one region hits the limit. Two clusters hashing to the same `/24` would fail at VPC create.
- **User-data size.** The limit is undocumented. The scripts are held to the repo caps, and the first create is the proof.
- **Controller replicas.** The CSI controller runs two replicas with required anti-affinity and no tolerations. A pilot-light standby with one untainted node (the master) leaves one replica Pending. Provisioning works with one; nothing waits on the controller rollout today (`scale.js` waits on the node DaemonSet).
- **Docker Hub pulls.** The node plugin pulls `vultr/vultr-csi` from Docker Hub with `imagePullPolicy: Always` on every pod start. Docker Hub rate limits are the exposure. Mirroring it needs the `vultr-csi` package flip.
- **Version channel.** vultr-csi's Kubernetes minor (36) is behind k3s (37). The channel already holds k3s patches for Linode's driver; Vultr would keep holding them after Linode catches up, until vultr-csi builds on 0.37.
- **No plan downgrades.** Vultr refuses a plan downgrade, so `vibecarbon scale` to a smaller master or worker type fails at the API, as it already does for Vultr compose.
- **Sources not checked from here.** The cost-grid prices come from Vultr pages that refused automated fetches here (403). The implementer re-reads them and records the date.
